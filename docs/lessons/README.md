# lessons：把"踩过的坑"记成可复用的资产

这个目录是**自进化的记忆**。一条 lesson = 一次观测到的失败 / 反馈 + 诊断 + 候选改动 + 验证结果。
机制出处：`AGENTS.md`「工作约定」与 `docs/MEMORY.md` 第④层（经验与模式）。

## 为什么要它

同一个问题被"发现两次"是纯浪费：第二次本该是"查一下 lessons → 已知 → 照上次那套修"，而不是从头诊断一遍。
**试过但无效的方案也要记**——不记的话，半年后有人会再试一次同样无效的做法。

**没有验证闭环的"自进化"只是提示词膨胀**：只加规则、不验规则，仓库最后会长成一堆看起来很对的条款，没人知道哪条真的在起作用。

## 格式（保持短，几条硬字段）

```md
# 一句话症状

- 状态：待验证 / 已验证有效 / 已验证无效 / 已废弃（带日期）
- 症状：（外部能观察到的现象）
- 证据：（命令输出 / 守卫报错 / 文件路径 / issue —— 没有证据的 lesson 只是猜想）
- 诊断：（根因；多个原因就分条）
- 候选改动：（改哪里、改成什么）
- 验证：（怎么证明它有效；**优先零成本验证**：守卫测试、脚本、链接/导入校验，只有行为类改动才值一次真评测，见 `docs/EVALS.md`）
- 棘轮：（这次进化固化成了什么：守卫测试 / lint 规则 / 脚本 / 规范条目）
- 遗留：（没解决的，以及为什么先不解决）
```

## 状态怎么流转

```text
观测到问题 → 待验证（写下诊断与候选改动）
           → 改 + 验（零成本优先）→ 已验证有效（把"棘轮"栏填上，并挂进 AGENTS 或对应规范）
                                   → 已验证无效（写清为什么无效，别再试）
```

- **"已验证有效"的判据是检查变绿**（或一段明确的命令输出），不是"我看了一遍觉得对"。
- 声称做了某事不算数：把命令和输出留在 lesson 里。漏写了检查就补检查，别只在正文里保证。

## 准入标准（什么才配变成规则）

- 一条规则要进 `AGENTS.md` 或 `docs/` 规范，必须能回答：**"哪个检查能证明它没被违反？"**
- 答不上来的 → 留在 lessons 里当"待验证候选"，**不要**写成规则。这是防规则膨胀的那道闸。
- 规则改动留一行痕：改了什么、为什么改、配套检查是哪个。

## 和评测的分工

- **lessons** 记"harness 自己该怎么改"（规则、守卫、脚本、命令）——小步、便宜、大多零成本验证。
- **某个能力值不值得用**（技能 / 子代理 / MCP）是另一回事：完整 A/B 结论在评测仓库 `harness-lab`，本仓库只留"装了哪个 + 一行理由"。
- 两者都可能成为进化的输入，但**别混**：harness 缺陷进 lessons，能力结论进 lab。
