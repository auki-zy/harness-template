# EVALS.md

轻量评测方法学：只解决一个问题——**"这条规则 / 这个能力到底有没有用"**。

本仓库不做重评测：完整的候选池、A/B 台账、判官与会话证据在评测仓库 `harness-lab`（`adopted/` 与 `evals/`）。
这里是"够用就好"的那一档：**偶尔跑一次，用来裁决争议**，不是日常流程。

## 什么时候值得跑

值得：

- 争议**没法靠零成本验证裁决**——改的是行为 / 指令 / 提示词，而不是可断言的代码路径；
- 收益与代价都大：要固化成人人遵守的规则，或要装进一个能力；
- 已经改了两版，还停在"感觉差不多"。

不值得：能用测试 / 守卫 / 类型断言直接钉死的（去写检查）、样式细节、纯文档措辞、心里已经有结论只是想要个背书。

## 最小流程（一次 A/B）

1. **定题**：一句话写清"有 X 和没 X，区别会体现在哪"，并定一个**可判定**的通过标准（不是"看起来更好"）。
2. **跑 A/B**：同一任务跑两遍——A 不给规则/能力，B 给；其他条件（模型、提示词、工作区输入）保持一致。
3. **判**：看**产物与过程**——改了哪些文件、命令跑没跑过、最终答复是什么。不要看哪边说得好听。
4. **记**：结论进 `docs/lessons/`（涉及 harness 规则）或一条 ADR；**必须写清是 n=1 还是重复跑过**。
   结论为"无效 / 分不出"同样要记——那也是一次有价值的结果。

## 三条硬规矩（都是真踩过的坑）

- **n=1 不是结论**：同一个 case 重跑可能直接翻转（同样的输入，一次全过、一次全挂都发生过）。单次差异先当噪声；要下结论就重复跑几次看是否稳定。
- **分不出作用要如实说**：如果 A 全过、B 也全过，这次评测**没有证明**规则有用。写"这条题分不出技能的作用"，不要硬写成"B 更好"——那是把噪声当证据。
- **判据要落在产物上**：让人能打开文件、看到 diff、读到命令输出。只看最终答复会被措辞骗（说得漂亮 ≠ 改了东西）。

## 与 lessons 的分工

| | 回答什么 | 成本 | 频率 |
|---|---|---|---|
| `docs/lessons/` | harness 自己该怎么改 | 低（守卫 / 脚本优先） | 每次踩坑 |
| 本文件（EVALS） | 有争议的规则改动值不值 | 高（A/B + 判读） | 偶尔 |
| `harness-lab` | 某个能力值不值得装 | 最高（台账 + 重复跑 + 判官） | 由 lab 集中做 |
